# Retained organization push capability storage

V136 stores push bindings in a separate organization table. A binding pins the space,
account, group device, original native parent and Matrix user/device. The opaque
capability uses `hrisgp1_`; company `hriscp1_` capabilities remain distinct and unchanged.
The binding does not contain an FCM/APNs token. A future delivery operation must resolve
that token from the current native push registration under fresh admission.

The original reservation, capability hash and encrypted value are immutable. Only
version 0 to 1 publication is possible; no reset/delete or parent-cascading foreign key
exists. The SQL trigger validates current root account scope, active group device,
native binding, credential version and native expiry. A retained LEGACY device also
requires its exact completed handover. Database time is checked after device lock waits.
Publication metadata alone never grants provider, callback, content or reply authority.

Owned reads survive offboarding and native-parent cleanup. An exact hash lookup is
restricted to the anonymous root lookup scope and only identifies the next account
and device to admit. The datasource restores its transaction-local lookup setting
before returning; another query in the same transaction cannot inherit the capability.
Cleanup preserves the primary technical exception, including cancellation/interruption.

The repository maps scoped records and validates both metadata and encrypted-value
bounds. Reservation and publication require exact post-write readback. A malformed or
missing readback fails the caller's transaction; an uncertain response can be recovered
by reading the retained original binding. Provider operations and caller admission are
not hidden inside the repository.

The distinct `hris:matrix-space-push:v1:` purpose authenticates eight newline-separated
coordinates: space, account, group device, original native session, Matrix user, Matrix
device, reservation microseconds and capability hash. Publication keeps this purpose
and ciphertext unchanged. Key rotation retains old decryption keys; a missing key does
not regenerate the capability. The schema136 recovery verifier projects exactly the
same coordinates while preserving every prior schema's envelope query.

Accepted tests cover real PostgreSQL ownership and lifecycle, concurrent writes,
expiry during lock waits, failed-result/cancellation rollback, exact readback, tampered
encrypted metadata, key rotation and archive restoration, including the recovery SQL
generated by the actual Python verifier. Actual completed LEGACY migration leaves
the original company push record unchanged and retains both records through parent purge.

This is storage only. Native managed pusher registration, group callback admission,
coalescing queue and worker delivery, logging redaction, Mobile background/reply ownership
and actual FCM product acceptance remain required. No group pusher is registered by this
change, and no shared DI is changed. All 54 PRD groups remain open; rollout stays disabled.
