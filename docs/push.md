# Mobile push delivery

`core/push` provides a domain `PushRepository`, an FCM HTTP v1 adapter, and the official Google Auth library for service-account OAuth. It is separate from [native registration](mobile-api.md#native-push-registration) and durable inbox publication. The inbox remains authoritative. A push is a short-lived synchronization hint; it does not authorize a resource or confirm that a device received it.

## Provider configuration

The transport is disabled by default. These settings belong to the process that sends notifications:

| Variable | Meaning |
| --- | --- |
| `HRIS_FCM_ENABLED` | Explicit provider opt-in; defaults to `false`. |
| `HRIS_FCM_PROJECT_ID` | Firebase project registered by the mobile applications. |
| `HRIS_FCM_CREDENTIALS_FILE` | Read-only mounted service-account JSON file, at most 32 KiB. |

Enable the Firebase Cloud Messaging API in the chosen Google Cloud project and grant the service account the minimum permission required to send FCM messages (`cloudmessaging.messages.create`). The configured project must match the credential file. Credential loading permits service-account files and the Google OAuth token endpoint only; it does not use arbitrary credential types, metadata-server discovery, impersonation endpoints, or request-supplied URLs. Keep the file outside Git; `*service-account*.json` is ignored. Rotate credentials through the deployment secret store.

Register Android/iOS in that Firebase project. Android needs its app-specific Firebase configuration. iOS additionally needs APNs credentials uploaded to Firebase, push entitlement, and the remote-notification background mode. The mobile client requests OS permission where appropriate, registers its FCM token through the backend, and processes foreground/reconnect sync. No live Firebase project or HRIS mobile application has been configured by these transport tests.

## Contract and ownership

Provider messages contain bounded string data. The caller supplies stable event/resource IDs and an absolute expiry no more than five minutes away. Android uses normal priority and a collapsible inbox hint; APNs uses a background notification with explicit expiration. No alert, announcement body, payroll amount, document URL, or employee name is generated by the adapter. Delivery of background hints is best effort, particularly on iOS and suspended/offline applications. The mobile client must synchronize on foreground/reconnect even if no hint arrives.

The repository coordinates the credential and FCM datasources. Datasources perform SDK/network I/O and return technical responses; they do not retry or choose recipients. `safePushCall` preserves existing failures and cancellation, and maps technical exceptions without exposing provider bodies, tokens, or credentials. An explicit `UNREGISTERED` FCM response is distinct from a rejected request. Invalid arguments, sender-project mismatch, and authentication errors must not silently erase every registered token.

The owned HTTP client rejects redirects, has a three-second connect timeout, and accepts at most 64 KiB per response, including chunked bodies. A ten-second deadline covers each complete OAuth/FCM exchange; timeout or interruption cancels its HTTP future and body subscription. The JDK header timeout alone is insufficient for a stalled body. OAuth SDK retries are disabled and synchronous refresh is shared by the SDK across concurrent callers. The worker owns delivery retries and deadlines. Diagnostic output is limited to safe codes, categories, and application frames; do not enable SDK payload debugging in deployment.

## Inbox dispatch

Inbox insertion captures one dispatch identity in the publication transaction. A failure rolls back publication, inbox, sync, and dispatch together. Reads, acknowledgements, and provider results do not create another dispatch. Existing inbox items from before this migration are not backfilled into push delivery.

The worker prepares one device at a time and stores its pinned session and completed-session cursor in PostgreSQL. Each step rechecks the original inbox recipient, current company/membership/read permission, account state, native session, credential version, registration state, and expiry. Only registrations created by publication time are candidates; later logins obtain existing messages through inbox sync. At most 500 historical session candidates can be processed per inbox, bounded by native issuance policy. No array of device tokens is copied into the queue.

Preparation locks announcement/company/member/account guards before the queue and native session. Provider I/O occurs after that transaction commits. Acknowledgement takes the account guard before the queue, and requires the current unexpired database lease. `UNREGISTERED` retires a token only if its registration version still matches; a replacement token is preserved. Token retirement and checkpoint advance roll back together if acknowledgement fails. A prepared message can already be in flight when permission is revoked or a session ends; push contains only opaque identifiers and an event code, and opening the inbox still requires fresh API authorization.

Four deliveries per process run without an executor waiting queue. Database leasing caps the deployment at 16 active push steps. Cleanup reads bounded candidates from separate indexed age/attempt ranges; claim-time predicates use a captured database instant so the due/lease indexes remain usable. Each lease lasts two minutes; an owned 60-second deadline cancels pending work. Polling, futures, HTTP bodies, timers, and task pools stop on shutdown. The shared deadline task binds cancellation to its own runner and cannot interrupt a later reused executor thread.

Transport failures and rate limits retry at most eight times per target, with five-second to five-minute exponential delays. A valid provider `Retry-After` delay/date can extend the delay, but never beyond the dispatch's 24-hour lifetime. Permanent rejection advances past that target. Repeated crashes or preparation/acknowledgement failures exhaust the fenced lease budget and mark the dispatch failed. A completed dispatch reports accepted/rejected counts; completion does not prove every device received or displayed a notification. Terminal audit and queue state commit together. External acceptance followed by a lost acknowledgement may cause a duplicate with the same event ID; mobile clients must deduplicate it.

Worker maintenance also runs while FCM is disabled: pending dispatches expire after 24 hours and terminal operational rows are removed in bounded batches after seven days. Inbox, immutable publication evidence, and audit remain retained. Disabling the entire worker also stops this maintenance.

## Mobile hint handling

The payload contains `schemaVersion`, `eventCode=communications.inbox_available`, `eventId`, `accountId`, `companyId`, and `inboxId`. Check the active account and recognized schema/event before acting. Translate the event code locally; do not use provider error text as product copy. Synchronize authorized inbox partitions before displaying local notification content. Hints can be collapsed, delayed, or absent, so foreground/reconnect sync is required independently. Deduplicate by account/company/event ID. Construct an internal inbox route from validated UUIDs; the payload carries no arbitrary external deep-link URL.

## Container opt-in

Set `HRIS_FCM_ENABLED=true`, `HRIS_FCM_PROJECT_ID`, and `HRIS_FCM_SERVICE_ACCOUNT_FILE` in deployment configuration, then include `compose.push.yml` alongside `compose.yml`. The override mounts the credential file read-only into the worker and does not enable the API sender. Give container UID `10001` read access to the secret while keeping it unreadable by unrelated host users. Missing host files are rejected instead of being created as directories. The API and worker still require the same identity decryption keyring for registered endpoints. See [delivery status](delivery.md) for checks actually performed; no live distribution is enabled by the repository.
